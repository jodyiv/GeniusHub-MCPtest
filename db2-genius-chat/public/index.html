How this app works

The problem

An AI model knows a lot about Db2, but it cannot see your databases. Without a bridge it can only guess – which is how you get invented tablespace names and made-up numbers.

The Model Context Protocol (MCP)

MCP is an open standard that lets an AI application discover and call tools exposed by another system, using one common format. Think of it as a USB-C port for AI: any MCP client can plug into any MCP server.

MCP client

The AI-facing application. In this demo that is this web app. IBM Bob, Claude Desktop and the Db2 Genius CLI are also MCP clients.

MCP server

Publishes a list of tools with names, descriptions and input schemas. Here: the Db2 Genius Hub MCP server (port 8000).

Tools

Functions such as get_tablespace or analyze_lock_waits. The server runs them against Db2 and returns structured results.

Why it matters here

  • Real data: every answer is built from a live tool result, not from the model's memory.
  • Read-only & governed: the Genius Hub MCP server runs read-only SQL and inherits the Genius Hub user's permissions.
  • One question, whole estate: the same tools can be repeated across every database profile (see the All databases tab).
  • Swap the brain freely: the model can be changed (Granite, Claude, GPT…) without touching the Db2 integration.
  • Nothing to hand-code per question: add a tool on the server and every MCP client can use it.

What happens when you ask a question

  1. You type a question – e.g. “Which tablespaces are almost full?”
  2. The web app asks the LLM (here IBM Granite via Ollama), including a short list of the MCP tools that look relevant.
  3. The LLM chooses a tool and its arguments – it does not run anything itself. It replies “call get_tablespace with these arguments”.
  4. The web app calls the MCP server with that tool call over HTTP (Streamable HTTP transport).
  5. The MCP server queries Db2 through Genius Hub, using the database profile you selected, and returns structured JSON.
  6. The LLM writes the answer from that JSON only. The raw rows also appear as a table so you can verify the answer.

For questions that span every database, see the All databases tab. Tip: the green chips under your question show exactly which MCP tools ran. Hover a chip to see the arguments the model chose, and click it to see the timing.

Asking about your whole estate

MCP tools work on one database at a time: you connect to a profile, then call a tool. To answer “which databases have…?” this app repeats the same tool call for every profile and compares the results. Pick All databases in the dropdown, or just ask a question containing “all databases”, “which databases” and so on.

  1. Understand the question – topic (space, backup, resources, health) and time window (“this week” = 7 days).
  2. List the profiles with fetch_dic_db_profiles.
  3. For each profile: connect_to_profile, then the relevant tools (below).
  4. Judge each result against fixed thresholds and sort the worst databases to the top.

Why the AI model is not used here

Comparing five or five hundred databases against thresholds is exact arithmetic. A fixed rule gives the same answer every time and cannot invent a number, so the app does this part in code and uses the AI model for open-ended questions about one database. This is a good pattern to explain to customers: use the LLM for language, use code for rules.

Reading the results

  • No data means a tool returned nothing usable – it is not counted as a problem.
  • A database that cannot be reached is shown as Critical with the error.
  • “No backup recorded in Db2 history” means Db2’s own history file is empty. Backups taken by external tools that do not write to Db2 history will appear this way.
  • Thresholds are constants at the top of fleet.js; adjust them to your client’s standards.
  • Cost: a full check is about 4–9 MCP calls per database and takes roughly 1–3 seconds each; the demo’s 5 databases took 5–11 seconds.

How the app connects

Signing in does three things, in order. A new token is requested every time you sign in, so no long-lived token is ever stored in a file.

1. Request a token from Genius Hub
# export GH_USER and GH_PASSWORD first, so the password never sits in your shell history
curl -X POST '<protocol>://<host>:<port>/dbapi/v4/auth/tokens' \
  -H 'Content-Type: application/json' \
  -d "{\"userid\": \"$GH_USER\", \"password\": \"$GH_PASSWORD\"}"
# → {"userid":"<user>","token":"eyJraWQi..."}
2. Open an MCP session, passing the token as headers
POST <mcp-url>
X-Genius-Hub-Hostname: <host>
X-Genius-Hub-Port:     <port>
X-Genius-Hub-Protocol: <protocol>
X-Genius-Hub-Token:    <token>
3. Pick a database profile

The app calls fetch_dic_db_profiles to fill the dropdown, then connect_to_profile when you choose one. Every later tool call runs against that database.

Using the same server from IBM Bob (or any MCP client)

Add this to .bob/mcp.json. Prefer an environment variable over pasting the token, because tokens expire.

{
  "mcpServers": {
    "db2-genius-mcp": {
      "type": "streamable-http",
      "url": "<mcp-url>",
      "headers": {
        "X-Genius-Hub-Hostname": "<host>",
        "X-Genius-Hub-Port": "<port>",
        "X-Genius-Hub-Protocol": "<protocol>",
        "X-Genius-Hub-Token": "${env:GENIUS_HUB_TOKEN}"
      },
      "disabled": false
    }
  }
}

Security notes

  • Your password goes only to Genius Hub to obtain the token; this app never stores it.
  • The token stays on the app's server. The browser only holds an opaque session cookie.
  • Sessions are closed (MCP logout) on sign-out and after 30 idle minutes.
  • TLS verification is off for the MCP endpoint because it uses a self-signed certificate. Install a CA-signed certificate and set INSECURE_TLS=false for production.

Troubleshooting

“Invalid Genius Hub user id or password”
The token request was rejected. Check the credentials in the Genius Hub web console.
“Could not reach the Genius Hub MCP server”
Confirm the MCP server is running and port 8000 is reachable from the machine running this app: curl -k https://<host>:8000/mcp (an HTTP 4xx/406 reply still proves it is listening). Check MCP_URL in .env.
“Session expired”
Sessions end after idle time, a server restart, or when the Genius Hub token expires. Sign in again – a new token is fetched automatically.
“I can’t answer this from live data”
A Db2 tool call failed and could not be recovered, so the app refuses to guess. The real reason is shown. If the MCP session was simply dropped, the app reconnects and retries by itself (see My session).
The profile dropdown is empty
Genius Hub has no database profiles for this user. Add one in the Genius Hub console, then press the reload button next to the dropdown.
Answers are slow
A CPU-hosted model needs 20–90 seconds per question. The tool chips show progress; the Db2 call itself normally takes about a second.
The model answered without using a tool
Small models sometimes skip tools. Rephrase with a clear action (“Show me…”, “List…”) or use one of the examples.
